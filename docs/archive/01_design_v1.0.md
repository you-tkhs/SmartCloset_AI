## 2. 実装方針

### 2.1 前提

本アプリは以下の3機能を中心として実装する。

- 衣服登録：スマホで撮影した写真をアップロードすると、AIが自動でセグメンテーション・メタデータ抽出を行い、クローゼットDBに登録する
- クローゼット閲覧：登録した衣服を背景透過画像としていつでも一覧・検索できる
- コーディネート提案：自然言語（今日の気分・予定）＋天気情報＋クローゼットの中身をLLMに渡し、最適なコーディネートを提案する

### 2.2 重視する観点

- 登録体験の速さ：ユーザーが写真を撮るだけで、カテゴリ・色・柄を自動付与する
- 非同期処理：重いAI処理はバックグラウンドで実行し、UIをブロックしない
- パーソナライズ：LLMの文脈理解を活用し、状況と心理に寄り添うコーデ提案を実現する
- スケーラビリティ：将来のファインチューニングやユーザー数増加に対応できる設計とする

### 2.3 開発ステップ概要

| ステップ | 内容 | 成果物 |
|---|---|---|
| Step 1 | AIロジックの検証（Pythonスクリプト） | 画像処理パイプライン（Jupyter Notebook） |
| Step 2 | バックエンドAPI＋DBの構築（FastAPI） | REST API・非同期タスクキュー・DB |
| Step 3 | フロントエンドの結合（Next.js） | 完成版Webアプリ |

## 3. システム全体構成

### 3.1 アーキテクチャ概要

本システムは以下のレイヤーで構成される。

| レイヤー | 技術スタック | 主な役割 |
|---|---|---|
| フロントエンド | Next.js / React / TypeScript | UI表示・カメラ/ドラッグ&ドロップ・API通信 |
| バックエンドAPI | FastAPI（Python） | REST API・認証・非同期タスク管理 |
| タスクキュー | Celery + Redis | AI処理の非同期実行・ステータス管理 |
| AIパイプライン | YOLOv8-seg / Vision LLM | セグメンテーション・カテゴリ/色/柄抽出 |
| LLM連携 | Gemini API / OpenAI API | コーディネート提案文の生成 |
| データベース | PostgreSQL（SQLAlchemy） | 衣服データ・ユーザー情報の永続化 |
| ストレージ | AWS S3 / GCS | 原画像・背景透過画像の保存 |
| 外部API | OpenWeatherMap等 | 現在地の天気・気温取得 |

### 3.2 データフロー概要

1. ユーザーがスマホで衣服写真を撮影・アップロード
2. フロントエンドがクライアント側で画像をリサイズ（640×640px）してAPIへ送信
3. FastAPIが即座に「受付済み（processing）」レスポンスを返す
4. Celeryタスクがバックグラウンドで YOLOv8-seg によるセグメンテーションを実行
5. 背景透過画像を生成し、カテゴリ・色・柄をVision LLMが抽出してDBに書き込む
6. フロントエンドがポーリングまたはWebSocketでステータスを監視し、完了後にクローゼット一覧を自動更新
7. コーデ提案時は気分・予定テキスト＋天気API＋DBの衣服リストをLLMに渡してレスポンスを表示

## 5. バックエンドAPI詳細設計

### 5.1 エンドポイント一覧

| メソッド | パス | 役割 | 非同期 |
|---|---|---|---|
| POST | /items/upload | 画像アップロード＋AIパイプライン起動 | ○ |
| GET | /items | 登録衣服一覧取得（フィルタ対応） | － |
| GET | /items/{id} | 衣服1件詳細取得 | － |
| DELETE | /items/{id} | 衣服削除 | － |
| GET | /items/status/{task_id} | AI処理ステータス確認 | － |
| POST | /coordinate/suggest | コーディネート提案生成 | ○ |
| GET | /weather | 現在地の天気情報取得 | － |

### 5.2 POST /items/upload 詳細

#### 入力

| パラメータ | 型 | 必須 | 説明 |
|---|---|---|---|
| image | File（multipart） | ○ | 衣服写真（JPEG/PNG、640×640px推奨） |
| user_id | string | ○ | ユーザーID |

#### 出力（即時レスポンス）

| フィールド | 型 | 説明 |
|---|---|---|
| task_id | string | Celeryタスクの追跡ID |
| status | string | "processing"（固定） |
| item_id | string | DBに仮登録された衣服ID |

#### 処理内容

1. 画像を受け取りクラウドストレージ（S3/GCS）に保存
2. DBに status=processing で衣服レコードを仮登録
3. Celeryタスク（ai_pipeline）を非同期起動
4. task_id・status・item_id を即座にレスポンス

### 5.3 GET /items 詳細

#### クエリパラメータ

| パラメータ | 型 | デフォルト | 説明 |
|---|---|---|---|
| user_id | string | 必須 | 対象ユーザー |
| category | string | なし | 例：Tシャツ、ジーンズ |
| color | string | なし | 例：黒、ベージュ |
| limit | int | 20 | 1ページの件数 |
| offset | int | 0 | ページネーション開始位置 |

### 5.4 POST /coordinate/suggest 詳細

#### 入力

| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| user_id | string | ○ | 対象ユーザーID |
| prompt_text | string | ○ | 例：「今日は大事な会議があるからカチッとしたい」 |
| latitude | float | ○ | 現在地緯度（天気API用） |
| longitude | float | ○ | 現在地経度（天気API用） |

#### 処理内容

1. 天気APIから気温・天候を取得
2. DBからユーザーの衣服リスト（カテゴリ・色・柄・画像URL）を取得
3. プロンプトを構築してLLM APIへ送信
4. LLMのレスポンス（提案テキスト＋推奨アイテムIDリスト）を返す

## 6. AIパイプライン詳細設計

### 6.1 パイプライン概要

| ステップ | 処理内容 | 使用モデル/ライブラリ |
|---|---|---|
| ① 画像リサイズ | クライアント側で640×640pxに圧縮してから送信 | JavaScript（Canvas API） |
| ② セグメンテーション | 衣服領域をピクセル単位で検出・マスク生成 | YOLOv8-seg（COCOプリトレイン） |
| ③ 背景透過 | マスクを適用して背景を透明にしたPNG画像を生成 | OpenCV / Pillow |
| ④ メタデータ抽出 | カテゴリ・色・柄・素材感をVision LLMが判定 | Gemini Vision / GPT-4V |
| ⑤ DB書き込み | 結果をPostgreSQLに保存・ステータスをcompleteに更新 | SQLAlchemy |

### 6.2 YOLOv8-seg 設定

- 使用モデル：yolov8n-seg.pt（初期）→ 精度不足時はyolov8l-seg.ptまたは独自ファインチューニング
- 対象クラス：COCOの衣類関連クラス（person, handbag, tie 等）を初期ターゲットとし、衣服専用クラスが不足する場合はアノテーション追加
- 信頼度閾値：0.4（調整可能）
- 入力解像度：640×640

### 6.3 メタデータ抽出プロンプト設計

Vision LLMへのプロンプト例（抽出項目）：

| 抽出項目 | 出力形式 | 例 |
|---|---|---|
| カテゴリ | 単一ラベル | Tシャツ・ジーンズ・パーカー・コート・スカートなど |
| 色 | 最大2色 | 黒・ベージュ・白・ネイビーなど |
| 柄 | 単一ラベル | 無地・ストライプ・チェック・花柄・グラフィックなど |
| シルエット | 単一ラベル | オーバーサイズ・スリム・フレアなど |

### 6.4 非同期タスクキュー設計

ユーザー体験を損なわないため、AI処理はCelery+Redisで非同期実行する。

| 項目 | 設定値/方針 |
|---|---|
| タスクキュー | Redis（ブローカー） |
| ワーカー数 | CPUサーバー：2〜4ワーカー（並列画像処理） |
| タイムアウト | 1タスクあたり最大30秒 |
| リトライ | 失敗時は最大3回リトライ、その後status=failedに更新 |
| ステータス管理 | item.status: processing / complete / failed |
| フロントへの通知 | ポーリング（3秒間隔）またはWebSocket |

### 8.3 画像アップロードフロー（フロントエンド側）

1. ユーザーが写真を選択 or ドラッグ&ドロップ
2. Canvas APIで画像を640×640pxにリサイズし、プレビュー表示
3. FormDataを生成して POST /items/upload に送信
4. レスポンスの task_id を保持し、3秒ごとに GET /items/status/{task_id} をポーリング
5. statusがcompleteになったら /closet の衣服一覧を再フェッチして自動反映

### 8.4 コーディネート提案フロー（フロントエンド側）

1. ブラウザのGeolocation APIで緯度・経度を取得
2. ユーザーが自然言語を入力して送信
3. POST /coordinate/suggest にprompt_text・lat・lngを送信
4. レスポンスの提案テキストを表示し、推奨アイテムIDをハイライト（ClothingCardの枠を強調）

## 10. エラーハンドリング詳細設計

### 10.1 エラー一覧

| エラー種別 | 発生条件 | 対応方針 | ユーザー表示 |
|---|---|---|---|
| 画像形式エラー | JPEG/PNG以外のファイルをアップロード | 即時エラーレスポンス（400） | 「JPEG/PNG形式のみ対応しています」 |
| ファイルサイズ超過 | 10MB以上の画像 | 即時エラーレスポンス（400） | 「10MB以下の画像をご利用ください」 |
| AI処理失敗 | YOLOによるセグメンテーション失敗 | Celeryリトライ3回 → status=failed | 「処理に失敗しました。再度アップロードしてください」 |
| LLM APIエラー | コーデ提案時のAPI呼び出し失敗 | リトライ1回 → エラーレスポンス（503） | 「提案の生成に失敗しました。しばらく後にお試しください」 |
| 天気API失敗 | 位置情報未取得またはAPI障害 | 気温なしでLLMを呼び出す（フォールバック） | 天気情報なしで提案を表示 |
| 未回答エラー | コーデ入力が空欄のまま送信 | バリデーションエラー（422） | 「気分や予定を入力してください」 |

### 10.2 フロントエンドエラー表示方針

- APIエラーはトースト通知で画面上部に表示し、3秒で自動消去する
- AI処理中はローディングスピナーを表示し、失敗時は「再試行」ボタンを表示する
- コーデ入力欄は空送信をボタン非活性で防止する

## 12. テスト観点

### 12.1 Step 1（AI検証）テスト

| テスト項目 | 確認内容 |
|---|---|
| セグメンテーション精度 | 様々な背景・照明条件の衣服写真でマスク生成が正確か |
| 背景透過品質 | マスク適用後のPNG画像に衣服の輪郭が綺麗に残るか |
| カテゴリ分類精度 | Tシャツ・ジーンズ等を正確に分類できるか |
| 色抽出精度 | 主要色を正しく抽出できるか |
| 処理時間 | 1枚あたりの処理がCPUで3秒以内に完了するか |

### 12.2 Step 2（API）テスト

| テスト項目 | 確認内容 |
|---|---|
| 即時レスポンス | アップロード後200ms以内に処理中レスポンスが返るか |
| 非同期処理 | Celeryタスクがバックグラウンドで正常実行されるか |
| ステータス更新 | 完了/失敗時にDBのstatusが正しく更新されるか |
| コーデ提案API | プロンプト・天気情報がLLMに正しく渡されるか |
| エラーハンドリング | 不正な入力・API障害時に適切なエラーレスポンスが返るか |

### 12.3 Step 3（E2E）テスト

| テスト項目 | 確認内容 |
|---|---|
| 登録フロー | 写真撮影→アップロード→クローゼット反映が一気通貫で動くか |
| コーデ提案フロー | テキスト入力→提案表示→推奨アイテムハイライトが動作するか |

| ポーリング動作 | AI処理中のステータス更新がUIに反映されるか |

## 13. 将来拡張を見据えた設計メモ

### 13.1 拡張候補

| 拡張項目 | 概要 | 優先度 |
|---|---|---|
| ファインチューニング | 衣服専用データでYOLOをファインチューニングし、セグメンテーション精度を向上 | 高 |
| コーデ履歴保存 | 過去の提案・着用記録を保存し、パーソナライズ精度を向上 | 高 |
| カレンダー連携 | Googleカレンダーの予定を自動取得し、プロンプトへ組み込む | 中 |
| SNS共有機能 | コーディネート結果をSNSに共有できるようにする | 中 |
| バリエーション提案 | 1回の提案で複数のコーデ案を並べて比較できるようにする | 中 |
| モバイルアプリ化 | React Nativeでネイティブアプリとして提供する | 低 |

### 13.2 今回見送る理由

- MVP段階ではコア3機能（登録・閲覧・提案）の品質を最優先するため
- 非同期処理とLLM連携の安定稼働を確認してから拡張機能を追加する

## 14. 実装時の注意事項

1. FastAPIのエンドポイントはすべて即時レスポンスを返し、重い処理はCeleryへ委譲すること
2. 画像リサイズはクライアント（Canvas API）で実施し、サーバーへの転送量を最小化すること
3. LLM APIキーは環境変数で管理し、コードに直書きしないこと
4. YOLOの信頼度閾値（0.4）は衣服の種類によって調整が必要なため、設定ファイルで変更可能にすること
5. PostgreSQLのUUIDはuuid_generate_v4()を使用し、連番IDは使わないこと（分散環境対応）
6. ストレージ（S3/GCS）への署名付きURLを使い、画像URLを直接公開しないこと

## 15. まとめ

本詳細設計は、SmartCloset AIをそのまま実装できる粒度で定義したものである。

特に以下を重視している。

- AIロジック（セグメンテーション・LLM）は独立したサービス層として設計し、差し替えが容易な構造にする
- 非同期タスクキューにより、ユーザー体験（即時レスポンス）とAI処理品質を両立させる
- フロントエンドは段階的に実装可能な設計とし、Step 1→2→3 の順に検証・結合する
- エラーハンドリングとステータス管理を設計段階から組み込み、本番障害時の対処を容易にする

本設計に基づき、次工程では以下を作成できる。

- Step 1：Jupyter Notebookによる画像処理パイプラインの検証
- Step 2：FastAPI + Celery + DBの実装とAPIテスト
- Step 3：Next.jsフロントエンドとAPIの結合・E2Eテスト
- 本番デプロイ手順書・インフラ構成図

## 16. 追記

機械学習プロジェクトはデプロイして終わりではない。なぜなら推論の精度はデータのドメイン変化などによって低下してしまうからだ。

そのため通常のウェブサービスよりもデプロイ後のモニタリングに注力する必要がある。

モニタリングも含めた機械学習プロジェクトの方法論を「MLOps」と言うのだ。

AIモデルは私が実装し、接続やアプリケーションの実装はコーディングエージェントに任せよう。
