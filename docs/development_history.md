# 開発経緯 — 技術的意思決定の記録

> 本書は開発記録(2026年5月〜7月)から技術的な意思決定を抽出して時系列で再構成したものである。
> PoCの評価基準・結果の正本は `evaluation.md` / `specification.md`、現行の実装設計は `design.md` を参照。

---

## 1. ベースライン構築(5/28)

画像を読み込み、YOLOで対象物を切り出し、LLMで属性を識別する——というパイプラインの最小構成を実装し、コンセプトが成立することを確認した。この時点で次の課題を設定した。

- COCOプリトレインの yolo-seg は衣類向けではない(person, tie 程度)。衣類特化のプリトレインモデルが存在しないため、**Fashionpedia でのファインチューニングが必要**
- 処理の関数化と、多様な衣類での効果検証

## 2. プリトレインモデルの限界調査(6/11)

やみくもに全クラスで学習する前に、「現状のモデルで何が検出でき、何ができないか」「プロダクトにはどのクラスが必要か」を棚卸しした。

- 必要なのは **アウター・トップス・ボトムス・シューズ・バッグ・アクセサリー(時計・サングラス・帽子・マフラー等)・ドレス**
- COCOプリトレインの yolov8n-seg では、多くの衣類は「クラス名は違えど何かとして検出」されるが、**アウターとシューズはそもそも検出されない**ことを確認

→ Fashionpedia(46クラス)によるファインチューニングを決定。ただし46クラス全てで学習するのは目的に対して非効率であり、クラス統合が必要と判断した。

## 3. クラス設計 第1版 — 7クラス(6/12)

Fashionpedia の46クラスは「服のメインカテゴリ(13)/小物(14)/パーツ(7)/留め具・装飾(12)」に大別される。パーツ・装飾はプロダクトに不要なので捨て、メインカテゴリと小物を **outer / tops / bottoms / dress / shoes / bag / accessory の7クラス**に統合するクラスマップを設計した(例: jacket・vest・coat・cape → outer、glasses〜umbrella の小物14種 → accessory)。

COCO形式からYOLO形式への変換、変換不可サンプルの除去までを前処理パイプラインとして実装した。

## 4. 学習と最初の壁 — accessory の寄せ集め問題(6/13〜6/15)

Google Colab で学習を実施。運用面では次の知見を得た。

- 3epochの動作確認 → その重みを初期値に15epoch、という**段階的な学習**で計算資源を節約できる(15epochを初期値に+5epochは、通しの20epochと同等)
- ランタイム切断時は `last.pt` から `resume=True` で再開できる(ハイパーパラメータも保存されている)

検証の結果、outer / tops など大きな衣類は問題なく検出できたが、**accessory はほぼ機能しなかった**。追加学習も6epochで精度改善が止まった。

原因を「accessory はメガネ・帽子・手袋・時計・靴下・傘など**形状がまったく異なる13種の寄せ集め**であり、単一クラスとして学習不可能」と診断。**クラスは意味でなく形状の均質性で切るべき**という教訓を得て、accessory を分割した13クラス(hat / watch / glasses / belt / neck_accessory / leg_wear / glove を独立)で再学習することにした。

## 5. ドメインシフトの発見(6/19)

13クラスで学習した結果、**Fashionpedia の検証データでは精度が出るのに、実際の入力を想定した画像では機能しない**という現象に直面した。

原因は**ドメインシフト**だった。

- Fashionpedia は「人物が着用しているファッション写真」にラベル付けされたデータセット。画像内の時計や帽子は**極めて小さい物体**として写る
- 一方このプロダクトが想定する入力は「その物体だけを撮った単品写真」。時計も帽子も**画面いっぱいの大きな1点物**として写る
- Tシャツやズボンの精度が良かったのは、単品でも Fashionpedia の着用画像とスケールが近いから。小物クラスはスケールが根本的に異なるため転移しなかった

このとき「事前学習済みモデルと実データの間にはドメインシフトが必ず生じうる。**だからAIサービスはデプロイして終わりではなく、MLOpsの考えに基づき継続的に評価・改善する必要がある**」ということを、講義ではなく自分のデータで体得した。これは現行設計(design.md 18.2節のモニタリング設計)の原点である。

## 6. データで解く — 9クラスへの確定(6/19)

実画像でクラスごとの得手不得手を定量的に洗い出した。

- **スケール差で認識できないクラス**: shoes / watch / glasses / belt / neck_accessory / leg_wear
- **形状が似たクラスに誤認するクラス**: outer(→tops)、bag(→bottoms)、hat(→tops)、gloves(→tops)

対処は「パラメータ調整」ではなく「**データの補強**」を選んだ。

1. 弱点クラスの単品画像を Roboflow Universe の instance segmentation データセットで補強(先頭のクラスIDをこのプロジェクトのクラスに書き換えるだけで統合できる)。補強枚数の例: shoes 1,976枚 / watch 1,688枚 / glasses 1,004枚
2. その過程で、bag の72枚(訓練54+テスト18)が **bounding box 形式の混入データ**でセグメンテーション学習のエラー源になることを特定し除去
3. belt / gloves / neck_accessory / leg_wear は**良質な補強データが見つからず、かつプロダクト上の重要度が低い**ため、認識対象から削除する判断をした(「認識できないクラスを残す」より「対応クラスを明示する」方がプロダクトとして誠実)

こうして最終の **9クラス(outer / tops / bottoms / dress / shoes / bag / hat / watch / glasses)** が確定した。

また、13クラスで学習済みの重みに9クラスを追加学習する案は、**破滅的忘却**(新データへの適応で既習クラスの性能が壊れる)の懸念から却下し、統合データセットで**ゼロから学習し直す**方針を採った。

## 7. 学習の成功とPoC(6/28〜7/12)

Fashionpedia+補強データの統合9クラスデータセット(train 52,784枚 / val 1,773枚)にデータ拡張(mosaic, copy_paste 等)を加えて30epoch学習した結果、**それまで認識できなかった小物クラスの強化に成功**した(モデルレベルの数値は `val_result_9class_30epoch_data_augmentation.md`)。

PoCの設計では、5章の教訓をそのまま反映した。

- **Fashionpedia の検証データではプロダクト性能を測れない**。そこで実ユースケース(単品写真)に沿ったテスト画像 **251枚** を独自に収集し、専用テストセットを構築した
- 評価基準を先に文書化した(`evaluation.md`)。YOLOは「クラス一致」ではなく「切り出せているか」を主評価とする(クラス判定はLLMの担当のため)
- 属性ごとの成功率/許容率に加え、プロダクトのKPIに直結する**最終登録判定**という複合指標を定義した

7/12、PoC完了。結果(YOLO許容率91.6%、最終登録許容率84.9% 等)は `specification.md` 11章を参照。

## 8. この経験からの学び

1. **モデルはベンチマークではなくプロダクトのドメインで評価する**。学習データのval精度は「そのデータ分布での性能」でしかない。実ユースケースの評価セットを自分で作ることに価値がある
2. **クラス設計は意味ではなく形状の均質性で決める**。「アクセサリー」という意味的なくくりは、視覚モデルにとっては13種の別物である
3. **改善はハイパーパラメータより先にデータ**。弱点クラスの特定 → 該当ドメインのデータ補強 → 混入不良データの除去、という順で効いた
4. **デプロイ後も同じ構造の劣化が起きる**。ユーザーの実画像分布は学習データから常にずれていく。だからモニタリングと再学習のループ(MLOps)を設計段階から組み込む(→ `design.md` 18.2節)
