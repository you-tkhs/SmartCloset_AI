# 実装を通じて得られた知見

> 本書は、design.md・todo.mdに基づくソフトウェア実装(Phase 0〜9、AIエージェント駆動開発、本番デプロイと運用後の改善サイクル)を通じて得られた知見をまとめたものである。
> AIモデル開発(PoC)を通じて得られた知見は [poc_history.md](poc_history.md) 8章を参照。

## 1. AIモデルのチューニングからシステムの実装まで一気通貫

　本プロジェクトではAIモデルを自分でチューニングし、その後動くものとしてソフトウェアの実装までも行うことができた。

　このパイプラインでは、画像ドメインの特化モデル(YOLOv8n-seg)と言語ドメインの汎用LLM(GPT-5.4-nano)という、性質の異なる2つのAIを役割分担させて組み合わせている。ピクセル単位の精密な切り出しは軽量な特化モデルに任せ、色・柄・素材といった柔軟な意味理解を要する属性抽出やコーディネートの提案理由づけは汎用LLMに任せた。加えて、切り出し後の背景透過画像をLLMに渡すことで認識精度を高め、登録時に一度抽出した構造化データをコーデ提案時に再利用することで画像推論の重複実行を避けるなど、精度とコストの両立を意識したパイプライン設計を行った。

　AI開発ではPoCを行うことが主な目的であるため、実際のプロダクトまで自分で落とし込む機会は多くない。今回の一気通貫を通じて、自分で開発したAIをユーザーまで届け、価値創出をすることができた。AIの社会実装の推進に向け確かな手触りを獲得できた。

## 2. 実際の運用を想定した設計書からのAIエージェント活用

　本プロジェクトではコーディングをAIエージェント(Claude Code)に委譲する前提で、実装着手前に約1,800行に及ぶ設計書を作成した。正常系だけでなく、アップロード処理の補償ロジック・冪等性・障害復旧・エラーコードの体系まで、実運用で起こりうる異常系を先に言語化した点が特徴である。設計変更は必ずコードに先立って設計書に反映するという運用を、初期実装から本番運用後の改善まで一貫して守った。

　ソフトウェア設計の経験は豊富ではなかったが、AIエージェントとの壁打ちを重ねながら仕様の曖昧さを一つずつ潰していくことで、実装に耐えうる粒度の設計書に仕上げることができた。この過程を通じて、異常系の洗い出しやエラーハンドリングの設計原則など、実務で問われる設計の勘所を実践的に身につけられたことも収穫だった。

　AIエージェントに実装を任せる場合、成果物の質を左右するのはエージェント自身の性能以上に、人間側がどれだけ曖昧さを排除した仕様に落とし込めるかだと実感した。設計経験が浅くても、AIとの対話を通じて専門的な設計品質に到達できるというのは、AIエージェント時代ならではの手応えだった。

## 3. デプロイ後、本番運用しながら改善サイクルを回す

　本番デプロイはゴールではなく、実運用を通じて設計の見落としを発見するための起点だった。固定都市の天気しか使えなかった問題や、コーデ提案が天気の話に偏りすぎてユーザーの用途・シーンを反映しなくなっていた問題は、いずれも実際にアプリを使ってはじめて気づけたものであり、設計段階のレビューだけでは発見できなかった。特にLLMを組み込んだ機能では、プロンプトの制約が「羽織る」といった理由付けで実際には守られていないケースを実機検証で発見し、確実な保証が必要な箇所はプロンプトではなくサーバー側のロジックで担保するという判断に至った。

　AIを組み込んだプロダクトは、コードとして正しく動くことと、LLMが意図通りに振る舞うことが別問題であり、後者は本番相当のデータ・状況でなければ検証しきれない場合があると学んだ。デプロイを開発の終着点ではなく改善サイクルの一部として位置づけ、設計書を更新しながら本番運用後も継続的に手を入れる体制を維持したことが、プロダクトとしての完成度を高めた。

## 4. 実装とレビューを分離し、第三者視点を組み込む

　実装を担当するAIエージェントとは別に、レビュー専任のエージェントによるコード差分の確認を各フェーズの節目で挟んだ。この結果、実装時には気づかれなかった不整合(ストレージ容量不足時のエラー分類やLLM呼び出し失敗時の扱いなど、設計書の記述と実装の間の細かな乖離)を複数回発見・修正できた。

　AIエージェントに開発を任せる場合でも、実装者自身によるセルフレビューには限界があり、視点を分離したレビュー工程を挟むことの効果は人間のチーム開発と変わらないと実感した。AIエージェント駆動開発は「エージェントに任せて終わり」ではなく、レビューや検証を含めた開発プロセス全体を設計する必要があると学んだ。

## 5. デプロイ手順を自ら見直し、再現性のあるコードに落とし込んだ

　当初の設計書ではOracle Cloud上のVM構築をクラウドコンソールでの手作業手順として定義していた。しかし実装を進める過程で、手作業では「VMが消失した場合に同じ構成を再現できるか」「設定変更を後から追跡・レビューできるか」という点に不安が残ることに自ら気づき、Terraformによるインフラのコード管理(IaC)へと設計を切り替えた。design-first運用に従い、まず設計書を手作業手順からTerraform管理の方針へ書き換えたうえで実装した。

　この切り替えは外部からの指摘や不具合報告を受けたものではなく、自分自身が書いた設計を運用の視点からより良いものへ改善しようとする中で得た気づきだった。実運用後に不具合を修正した改善サイクル(前々項)とは異なり、問題が顕在化する前にリスクを見越して設計を先回りして直す、予防的な改善の経験になった。インフラを「一度動けばよいもの」ではなく「再現可能な資産」として扱う姿勢を得られたことは大きな収穫である。
